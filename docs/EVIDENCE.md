# Evidence and limitations

Harbor Exchange is fictional. Its evidence combines the station path map and maintenance notice in one [commit-pinned JSON fixture](https://raw.githubusercontent.com/amzar1st/AccessRoute-/ab2e31740e758c8e167ed7c92e5d86a2e3ac15ec/evidence/harbor-exchange.json). Every validator checks the file's SHA-256. It models a north entrance outage, a south entrance available throughout the window, and one shared transfer lift. Both proposed routes must match the topology and equipment dependencies in the evidence to receive a supported verdict.

The NYC adapter fetches the public [MTA current and scheduled elevator outage feed](https://api-endpoint.mta.info/Dataservice/mtagtfsfeeds/nyct%2Fnyct_ene.json), listed in the [MTA developer resources](https://api.mta.info/#/EAndEFeeds). It matches exact elevator IDs, excludes escalators, and applies half-open time intervals in New York wall time. It treats windows near ambiguous daylight-saving transitions conservatively. The canonical report records up to eight distinct matching outage windows per elevator per leg. Notice end times are estimates. Reported outages can be rescheduled and the live feed changes. A finalized report represents what the validators agreed on at assessment time. It carries the matched IDs and normalized notice windows, while the link points to the current feed.

The live adapter checks equipment cited by the user. It does not prove that a station leg's labels match the equipment inventory or that the itinerary includes every required lift. A reported outage blocks a user-declared dependency. A clear-looking feed cannot prove that a lift is running, that an entrance is open, or that a connection will be usable. Real-world support decisions require a versioned agency path graph plus affirmative operational evidence. That is the path to supporting real-world alternatives in a future release.

Both sources are contract constants. Validators do not fetch rider-selected hosts or execute source text. Requests and report size are bounded. Source errors or unknown evidence become insufficient evidence. If validators receive relevant changes between fetches, strict equivalence can lead to undetermined consensus. The browser treats that outcome separately from a finalized failure. A second check uses a fresh request ID and creates a separate record.
